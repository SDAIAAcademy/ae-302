Anatomy of a harness

The model is one part; the harness is the rest

Tools

Typed contracts, useful errors, checks in code.

Context

Prompt, context file, skills, budgets.

State

History, the database, sessions, traces.

Feedback

Stop rules, gates, verification, evaluation.

The same model behind two harnesses is two different agents. Most of this course's engineering is in these four boxes.

Map Days 1 and 2 onto the boxes: typed tools (tools), compaction and skills (context), traces (state), stop rules (feedback). Today fills the feedback box: gates, verification, evaluation.

These are predictions, not results: the course's runs used a scripted model, which does not react to a removed part. A part that breaks nothing on ten tasks is untested, not useless: the step budget only matters on the run that loops. That is why the capstone asks for tasks that exercise each part.

A durable habit

Re-test the scaffolding when the model changes

  • Some harness parts compensate for a weak model: long prompts, extra checks, forced steps.
  • A stronger model may not need them, and they still cost tokens and latency.
  • Other parts never go: the write gate and the ownership check protect people, not the model.

The method is the lab

Remove one part, run the evaluation, keep the part only if the numbers say so, or if it protects someone.

The entry lists "removing scaffolding as models improve" as durable knowledge. Ask: which of Bosla's five parts would you remove first if a new free model scored perfectly without it? Which never?

Lab 3.2 · step 1

The SDK on a free model: wrap a client, list the tools

client = AsyncOpenAI(base_url=OPENROUTER, api_key=key)
model = OpenAIChatCompletionsModel(model=K.MODEL, openai_client=client)
tools = [function_tool(t) for t in p.tools()]
bosla_sdk = Agent(name="Bosla", model=model, tools=tools,
                  instructions=port.SYSTEM_PROMPT + CONTEXT_FILE)
result = await Runner.run(bosla_sdk, task, max_turns=8)

function_tool reads the same type hints and docstrings as K.tool_schema, so the eleven port tools convert unchanged; the course checked this conversion. Tracing is switched off because the SDK exports to OpenAI's dashboard by default; with a free OpenRouter model there is nowhere to send it.

One step further

Hosted agents: the provider runs the loop and the tools

What you get

No loop to operate; built-in tools such as search or code execution in the provider's sandbox.

What you give up

Where the data goes, which tools run, what is logged, and whether the same agent runs on another model.

For Marsa. The booking list holds personal data classified Restricted (TC-05). Before any hosted option, ask where it would be processed and stored, against the Personal Data Protection Law.

No lab uses a hosted agent: they are vendor-specific and usually paid. The point is the trade-off and the data question, which the Day 4 security session returns to.

  • Kind of vessel against kind of berth

Lab 3.3 · step 3

The loop may not stop while the check fails

callcreate_booking(V-108, B03, 2026-11-15, 2 days) → BK-24031
stop?"Booked BK-24031 at B03."
guardVerification failed: under-keel clearance at B03 is 0.8 m ...
callfind_windows(V-108, 2 days, from 2026-11-15)
callamend_booking(BK-24031, berth B01)
final"B03 leaves 0.8 m under the keel (TC-03), so I moved BK-24031 to B01."

From the course's run with the scripted model: the check, the guard event and the database states are real; the model's moves are scripted. With verification the run ended with no rule broken; without it, BK-24031 stayed at B03. The fix rounds have their own budget: two, then the answer must say what could not be fixed.

Found by the same check

BK-24022 breaks the same rule, and Bosla did not make it

  • Najm Coral was already booked at B03 from 2026-11-03.
  • Bosla's run did not create it, so the loop does not touch it.
  • Someone must hear about it: the duty harbour master, not the shipping agent's chat.
Scope of a fix. An agent that repairs everything it notices changes records nobody asked it to change. Report, do not fix.

This sets up Day 4: changes that affect safety go to Captain Huda Al-Harbi, the duty harbour master, through an approval gate. Ask the room how they would raise BK-24022 without giving Najm's agent a tool to change other bookings.

04
Evaluating agents

One run is an anecdote; five trials are a measurement

  • The model samples, so the same task can pass and then fail.
  • Twenty tasks, five trials each, a hundred runs.
  • Fresh samples only: switch the response cache off, or five trials are one answer replayed.

Two questions

Can the agent do the task? It passed at least once. Can we rely on it? It passed every time.

The cache that saved quota all week is now a trap: identical requests replay, so repeated trials must run with use_cache=False. LO5 asks for success in every and in any trial, and cost per completed task.

Two kinds of grader

Code where you can, a model where you must, and check the model

Code grader

Strings in the answer, the database after the run, no write when none was asked. Exact, cheap, repeatable.

Model grader

A rubric: "refuses without saying whose booking it is, cites TC-05". A verdict and a reason.

A grader is a model too. Label five answers yourself and compare. Disagreement is a finding about the grader or the rubric.

Five of the twenty tasks carry a rubric (T08, T10, T15, T17, T19): language, tone, what not to reveal. A run passes when the code grader and, if there is a rubric, the model grader pass. The judge runs at temperature 0 and still varies; that is why the stretch asks for a human check.

0.90
success per trial

Every task can be done; eight of twenty cannot be relied on. The shipped recordings are synthetic: your own trials replace them.

Be explicit: the 100 recorded runs shipped with the course were written by a seeded generator (labs/_tools/make_reference.py), not by a model, because the course was built without a working key. The grading code and the arithmetic are real; the numbers illustrate the gap between pass@5 and pass^5. The stretch records real trials of three tasks.

Cost per completed task

Divide the cost of every run by the runs that succeeded

PRICE_IN, PRICE_OUT = 0.20, 0.80  # assumption
total = (in_tokens * PRICE_IN
         + out_tokens * PRICE_OUT) / 1e6
cost_per_completed = total / passed_runs
  • Failed runs cost money too; the task still has to be done.
  • Free models cost nothing: price the tokens as if on the model you would deploy.
  • A cheaper design that fails more can cost more per completed task.

The prices are placeholders the lab states as assumptions; replace them with the price list of the model you would deploy, from its official page. The capstone README reports cost per completed task, so participants should carry this calculation into it.
