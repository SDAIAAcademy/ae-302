How a reply gets written

Generation is a loop: predict, pick, append, repeat

→

3 · Appendit to the input

4 · Stopon a stop token or a length limit

Sampling

The pick is random within limits: the same task can end differently. Day 3 grades over five trials.

Output costs more

Input is read in one pass; each output token is another pass.

Length limits cut

Hit the cap and the reply stops mid-sentence, or mid-tool-call.

Reveal the three cards one by one. Sampling is why two participants get different wording in the same cell, and why the course grades agents over repeated trials. The last card sets up the Session 3 checkpoint: a tool call cut by the length limit must not be run.

The answer to "how does it remember?"

The model remembers nothing between calls

call 1system · user: "My booking is BK-24017."
reply"Thanks. What would you like to know?"
call 2system · user · assistant · user: "Which berth?"

Stateless

Each call is independent: your code resends the history.

Context window

The most tokens one call can hold, input plus output. All the model knows about the task must fit.

History costs money

Every call pays for the whole conversation again. Day 2 budgets it.

This answers the question from two slides ago: the product keeps the history and resends it. Through an API, that job is yours, and in an agent the history grows with every tool result. That growth is Day 2's whole subject.

Calling a model from code

A model call is one HTTPS request

from openai import OpenAI

client = OpenAI(base_url="https://openrouter.ai/api/v1",

resp = client.chat.completions.create(
    model=K.MODEL,          # a free open-weight model

One client, many servers

Change base_url and the same code talks to a gateway, a cloud host or your own server.

Free means shared

Free models are rate-limited. A busy one answers HTTP 429: retry, then fall back to the next model.

Nothing magic: a key, a JSON body with the model and the messages, JSON back. Every SDK this week wraps a request like this. agentkit adds retries, a fallback list of free models and a response cache; the free model names in agentkit.py change every few weeks, so check them the week before the cohort.

Describing the shape of the data

A schema is a contract the model cannot break silently

class BerthRequest(BaseModel):
    vessel_name: str
    arrival: date
    days: int = Field(ge=1, le=14)
    kind: Literal["container", "general",
                  "dry_bulk", "ro_ro", "tanker"]
    dangerous_goods: bool
    agent_code: str = Field(
        pattern=r"^[A-Z]{3}-\d{4}$")

Types and enums

A date is a date; a kind is one of five.

Constraints

Days from 1 to 14 is circular TC-08 written as code.

One source

Pydantic writes the JSON Schema from this class and validates replies against it.

Every constraint here is one fewer silent error. Ask: which business rule of the port became which line? days: TC-08's 1 to 14. kind: TC-03's berth kinds. agent_code: the booking service's format. The same JSON Schema will describe every tool argument in Session 3.

Structured outputs

Ask for the schema; validate anyway

schema = BerthRequest.model_json_schema()

       "json_schema": {"name": "BerthRequest",

Constrained generation

Where the server enforces the schema, only tokens that keep the JSON valid can be picked.

Not every server enforces it

Some free models treat it as a hint. So the schema also goes in the prompt, and every reply is validated.

Tie back to the generation loop: enforced structured output restricts the pick step. Responses puts the same schema under text.format; Messages has its own field. The rule for the week: request the schema where supported, validate always, repair, then fail loudly.

Checkpoint

Is a response format enough?

Your extractor sends a JSON Schema response format, and the server accepts it. What else must your code do?

Nothing: the reply is guaranteed to match the schema
Retry the same request until a reply parses
Repair until valid, with no limit on attempts

What the model sees

The model sees a name, a description and a JSON Schema

def create_booking(self, vessel_id: str,

        agent_code: str,
        dangerous_goods: bool = False) -> dict:
    """Create a berth booking. Writes to the

    Args:
        berth_id: B01 to B08.
        arrival: arrival date, YYYY-MM-DD.
        ..."""

K.tool_schema(fn) turns hints into JSON Schema and the docstring into descriptions.

Loose types

berth_id is any string, arrival any text, days any integer. The service will refuse many of them.

Lab 1.3 step 1 prints this schema. The definition is sent, and paid for, on every call. Ask: which arguments can the model fill with values the service refuses? berth_id, arrival and days. The next slide tightens them.

Tightening the contract

Typed arguments turn guesses into enums and ranges

class BookingArgs(BaseModel):
    vessel_id: str = Field(pattern=r"^V-\d{3}$")
    berth_id: Literal["B01", "B02", ..., "B08"]
    arrival: date
    days: int = Field(ge=1, le=14)
    agent_code: str = Field(
        pattern=r"^[A-Z]{3}-\d{4}$")
    dangerous_goods: bool = False
  • Enums for closed sets: the model reads the eight berths in the schema itself.
  • Formats and ranges: dates as dates, days 1 to 14.
  • An example in each description: "V-110", "NJM-4417".
  • One job per tool, named for what it does.

The schema of BookingArgs replaces the generated one through a __tool_schema__ attribute. Fewer, well-typed tools beat many thin wrappers: every definition costs tokens on every call. A type is checked before the service is touched; a description is only a request.

Definitions

An agent is a model using tools in a loop

Workflows: models and tools orchestrated through predefined code paths. Agents: models dynamically direct their own processes and tool usage.

Who picks the next step?

Your code: a workflow. The model: an agent.

Who says it is done?

The model proposes; your stop rules decide.

Start simple

One call if it works, a workflow if the path is known, an agent only when it is not.

Session 3's round trip, repeated until a stop rule fires, is the whole idea. The source is Anthropic's Building effective agents, listed in the course sources. Autonomy is a cost: latency, tokens, variance and attack surface. Earn it with a test that shows the simpler design fails.

The core of every agent

The loop fits on one slide

for step in range(1, max_steps + 1):
    msg = K.chat(messages, tools=tools)...message
    messages.append(msg.model_dump(exclude_none=True))
    if not msg.tool_calls:
        return done(msg.content)        # model: done
    this = [(c.function.name, c.function.arguments)
            for c in msg.tool_calls]
    if this == last:
        return stop("repeat")           # no progress
    last = this
    for c in msg.tool_calls:
        out = K.call_tool(by_name, ...)
        messages.append({"role": "tool", ...})
return stop("max_steps")                # budget spent

Three exits

The model stops calling tools; the same calls repeat; the step budget runs out.

The history is the memory

Every step resends everything, so input grows each step.

Tools never raise into the loop

Errors come back as results.

Participants write this in Lab 1.4 without an assistant. Walk through each exit and ask which one is the model's decision and which two are the loop's. The repeat rule is cheap insurance: a model that asks for the same thing twice in a row is not making progress.

Explicit completion criteria

Decide in advance what "done" means, and what "stuck" means

ExitDecided byReturned as
No tool calls in the replythe modelstopped: "done" and the answer
The same calls as the last turnthe loopstopped: "repeat", no answer
Step budget spentthe loopstopped: "max_steps", no answer
Cost budget spentthe loop (Day 3)stopped: "max_cost"
A stop is not a success. "done" means the model stopped; whether the task was done is the grader's call.

The outcome LO1 asks for explicit completion criteria. Say which exits exist and return the reason, never silence. Then separate stopping from succeeding: Lab 1.4 grades every run by code, against strings in the answer or the state of the database.

The loop's fix

The repeat rule and the step budget bound the run.
